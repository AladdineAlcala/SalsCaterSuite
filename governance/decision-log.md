## Technical Rulings Added After The Debater's Plan Review (2026-10-22)

| **DEC-115** | 2026-10-22 | Financial | **The money chain carries one rounding**: two decimals, away from the midpoint, applied once in the Application layer, and the create path stores exactly the rounded values | CONFIRMED | BI Architect, on the Debater's blocking finding F2 | `DiscountPercentage` is stored as `decimal(18,4)` while every money column is `decimal(18,2)`, and `Booking.RecalculateFinancials` performs raw arithmetic. Without a single rounding, a percentage discount of `0.005` on a gross of `100.00` yields a stored `AmountDue` of `99.99` or `100.00` against a calculator figure of `99.995` - a half-cent divergence on one booking, and a reconciliation failure across a population. The rule is BR-20's existing convention (two decimals, away from the midpoint, once, in the Application layer) applied to the money chain, and it is what makes `Booking.AmountDue == calculator.NetAmountDue` true **exactly** rather than approximately. The browser never re-rounds. Every pinned expectation in the existing suites is a whole peso amount, so the change is a no-op on all of them. |
| **DEC-116** | 2026-10-22 | Data / Financial | **The out-of-town surcharge is a stored frozen column** (`Booking.ExtendedAreaAmount`, `decimal(18,2) NOT NULL DEFAULT 0`), not an inference from `Subtotal - PackageAmount` | CONFIRMED | BI Architect, on the Debater's blocking finding F4 | The inference has three defects. (a) `Subtotal` **conflates** the surcharge with the add-on total and the other charges, so `Subtotal - PackageAmount` silently changes meaning the day add-ons exist (RSK-048). (b) `ApplyExtendedAmount` is a **publicly settable** flag, so flipping it after creation would change what the calculator charges while the stored `Subtotal` still carried the surcharge. (c) A value that is a *derived difference* is not *frozen* in the sense BR-04 requires. The surcharge therefore becomes its own column, written once, read directly by the calculator. `ApplyExtendedAmount` becomes a creation-time switch and an audit marker rather than a money switch. The migration remains purely additive: three nullable columns and one `NOT NULL DEFAULT 0`. A pre-existing row's surcharge is `0`, which is the truth - no booking has ever been charged one. |
| **DEC-117** | 2026-10-22 | Domain / UI | **The payment states are named `AwaitingDeposit`, `PartiallyPaid` and `Settled`** so they never collide with the `BookingStatus` lifecycle vocabulary | CONFIRMED | BI Architect, on the Debater's blocking finding F5 | Contract section 5 publishes the ten `BookingStatus` names, and two of them - `DepositPaid` and `FullyPaid` - are *payment* names. A payload that carried both a lifecycle status and a payment state would have shipped two different meanings under one name, and a client that keyed on the string would have conflated them. The two vocabularies now never share a name: `BookingStatus.DepositPaid` is a **lifecycle** status, `PartiallyPaid` is a **payment** state. The three states remain mutually exclusive and exhaustive, and `Settled` deliberately covers the zero-value booking and the overpayment, neither of which may be reported as awaiting anything. |
| **DEC-118** | 2026-10-22 | Financial / Policy | **BR-05's overpayment prohibition is enforced** on the payment path and on the create path | CONFIRMED | BI Architect, on the Debater's blocking finding F1 (the reachable edge case) | BR-05 states that "total payments recorded must not exceed Net Amount Due unless explicitly flagged and acknowledged as an advance credit", but **no guard implements it**: `Booking.RecordPayment` rejects only a non-positive amount and a payment on a cancelled booking, and `POST /api/payments` has no check. The register publishes a `Settled` state that **includes** an overpayment and a balance that clamps at zero, so an unguarded overpayment would let a booking report `Settled` while it owes money that no surface can show - the exact "null-as-zero" class of defect the workplan forbids. A payment that would take the total above the net amount due is refused with `400`, and **nothing** is written: no payment row, no status change, no change to the cached `AmountPaid`. The guard does **not** apply to a refund (BR-06). The "unless explicitly flagged and acknowledged as an advance credit" clause remains an **open owner question** - no advance-credit mechanism is implemented, so an overpayment is refused rather than accommodated. |
| **DEC-119** | 2026-10-22 | Domain / UI | **The package tier code is not rendered** - `Package` carries no code column | CONFIRMED | BI Architect, on the Debater's clarification | The reference's tier block shows a code chip (`PKG-PREM-26B`). `Package` has no code column: its identity is `PackageId` and its display name is `Description`. A code is therefore not rendered rather than fabricated from the description or the id - the same discipline the packages catalogue already applies to a tier's food cost, course allocation, inclusions and venue coverage (DEC-067). The tier block shows the id and the description. |
